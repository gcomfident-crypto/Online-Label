# Skill 02：任务与状态流转沉淀

## 目标
把 LabelHub 的任务生命周期、审核生命周期和关键接口可靠性沉淀为项目内约束，确保任务从创建到导出可追溯、状态一致、失败可定位。

## 适用范围
仅适用于本项目中和任务流转有关的模块，包括：
- Owner 任务管理
- Labeler 领取、标注、提交
- AI 预审
- Reviewer 人工复核
- Labeler 修改后再次提交
- 终审与导出
- AI Agent 质检流转页面

## 执行原则
- 状态语义先于 UI 文案：先确认真实状态，再决定页面展示。
- 不允许页面之间各自拼状态；状态展示必须来自统一 DTO、状态机或共享转换逻辑。
- 用户可见任务 ID 必须使用 `T-0001` 这类展示编号，不把后端原始 ID 暴露到页面。
- 状态推进必须可追溯：谁触发、何时触发、从什么状态到什么状态、为什么触发。
- 错误不能静默吞掉，也不能用 mock 值掩盖；应给出明确、可定位的异常信息。

## 已沉淀标准
- 任务 ID 展示：
  - 使用 `apps/web/src/pages/owner/taskDisplayId.ts` 中的展示编号规则。
  - 表格需要任务 ID 时新增独立 `任务ID` 列，不把编号拼到任务名里。
- AI 机审队列：
  - 按任务级批次展示，不按单题拆开。
  - 最左侧任务 ID 必须和任务管理页一致。
  - AI 建议状态要保持“建议通过 / 建议打回 / 等待预审 / 失败”的明确区分。
- 质检流转：
  - 表格以任务为主线展示完整链路；
  - AI 预审进度、Reviewer 复核、最终完成必须分列展示；
  - 任务名称列不能挤占流程进度列的可读空间。
- 人工审核：
  - 聚合到任务级列表；
  - 点击任务进入详情；
  - 列表只展示用户能决策的信息，不暴露原始数据库 ID。
- 导出：
  - 只导出终审通过数据；
  - 上传源字段顺序和标注字段顺序必须稳定；
  - 不允许未终审通过的数据进入导出预览或导出文件。

## 交付后可靠性检查
每次完成和任务流转相关的开发后，必须检查以下三个报错是否仍可能出现：

- `AI 预审接口请求失败，请稍后重试。（HTTP 500）。`
- `领取任务接口请求失败，请稍后重试`
- `任务质检流水线加载失败，请稍后重试`

检查要求：
- 覆盖领取任务链路、提交后 AI 预审链路、AI Agent 质检流转加载链路。
- 如果出现 HTTP 500，必须定位后端异常来源，不能只改前端文案。
- 错误日志应能定位任务 ID、用户 ID、请求路径、状态码、时间戳。
- 前端应提供明确失败状态或重试入口，不让用户停在无反馈状态。
- 修复完成后要用窄测试或真实页面验证关键链路。

## 修改任务流转时的检查清单
- 是否改变了任务状态或审核状态。
- 是否影响任务 ID 展示。
- 是否影响 Labeler 领取、提交、修改、再次提交。
- 是否影响 AI 预审入队、重试、完成、失败。
- 是否影响 Reviewer 复核、打回、通过、修订通过。
- 是否影响终审通过与导出边界。
- 是否同步更新了列表、详情、时间线、统计字段。
- 是否有测试覆盖关键状态和失败路径。

## 评审口径
这套 skill 说明 LabelHub 的核心不是单点页面，而是任务从创建、领取、标注、AI 预审、人工复核到导出的工程化闭环。每个状态都有来源、边界和追溯信息，系统因此能支撑长期迭代，而不是一次性演示流程。
