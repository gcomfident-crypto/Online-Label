# Skill 02：任务与状态流转沉淀

## 目标
把任务从创建到结束的流转固化为可追溯、可验证、可扩展的状态系统，而不是页面间拼接的临时流程。

## 适用范围
仅适用于 LabelHub 的任务生命周期与审核生命周期，包括 Owner/Labeler/AI Agent/Reviewer 的端到端流转。

## 核心方法
- 以状态机替代“按钮驱动式自由流转”：
  - 明确合法流转边界（谁能从哪个状态进入哪个状态）。
  - 禁止非法跳转；异常状态只通过明确补偿动作处理。
- 将任务状态与子流程（AI 预审、人工复核、终审）关联起来：
  - 任务提交后触发 AI 预审队列；
  - AI 结论与人工复审结果共同决定后续路由；
  - 终审通过后才允许进入可导出路径。
- 使用审计日志闭环每次状态变更：
  - 记录变更人、时间、来源、目标状态、触发原因。
  - 页面上保留可追溯信息用于复盘与问题定位。

## 关键原则
- 状态语义先于 UI 文案：先定义 `状态`，再决定按钮和文案。
- 任务 ID 显示与内部主键分离：给用户展示统一可读编号，内部 ID 用于存储和追踪。
- 失败可重试：关键异步链路（AI 预审、导出）保留可重试策略，不因偶发失败丢失任务。
- 版本化可追溯：AI 规则、评分维度、模板变更时，历史审核引用历史版本。

## 交付后可靠性检查（必做）
- 每个迭代完成后，必须执行一次提交链路回归，确认以下错误不再出现或能被明确处理：
  - `AI 预审接口请求失败，请稍后重试。（HTTP 500）。`
  - `领取任务接口请求失败，请稍后重试`
  - `任务质检流水线加载失败，请稍后重试`
- 这三类报错属于流程级故障，出现时必须保留可追溯上下文（任务ID、用户ID、请求/trace标识、时间戳、状态码），不能仅停留在“文案显示”。
- 失败分支需要有明确恢复动作：
  - 前端提供可见重试机制，不让用户进入无效状态；
  - 后端记录可重放日志，供下一次提交修复；
  - 若问题由下游依赖导致，必须触发对应服务方告警或重试策略，不允许长期压在前端兜底。
- 通过该检查可把“链路健壮性”纳入工单标准，而非仅作为线上排障现象。

## 交付物
1. 后端：状态枚举、过渡规则、状态变更服务/审计落库。  
2. 前端：页面以状态驱动展示，不依赖分支拼接实现流程。  
3. 数据治理：导出、重试、时间线、详情页从同一状态源读取，不再出现口径偏差。

## 评审口径（你要讲给评审的内容）
- 这是“业务流程工程化”：状态是单一事实来源，不是多个页面各说各话。  
- 任何审核动作都能追溯“为什么到了现在”，降低争议与排障成本。  
- 这种设计直接支撑稳定交付和长期迭代，而不是一次性演示工程。

## 成果指标
- 非法状态跳转可被机制性阻断。
- 同一任务在各端页签展示的一致性提升（同一时间线、同一结论、一致来源）。
- 异常场景可追溯：能明确定位“是谁在什么时间把状态推进到当前节点”。
